# STUN-NAT

独立的 STUN 内网穿透管理系统，按 Lucky 的 STUN 模块工作方式实现：在一台设备上维持 TCP 或 UDP 的 NAT 映射，获得动态公网端口，再将流量转发到指定内网服务，或交由路由器直转。

它不是双节点 P2P 打洞系统，也不提供中继服务。映射是否可用取决于运营商和每一层 NAT 是否为 NAT1（全锥形）。公网端口不可指定，变化周期也无法保证。

## 功能

- Web 管理页面、会话登录、HTTP Basic Auth 和规则 REST API。
- 多条 IPv4 TCP / UDP 穿透规则。
- 通道监听端口支持固定值或 `0` 随机分配。
- TCP 使用同源端口保活连接和 STUN TCP 探测；UDP 持续保活并周期性探测。
- 本机代理转发模式：由本机 NATMap 进程将 TCP/UDP 流量转发到 `目标地址:目标端口`。
- bind 直转模式：只建立 NAT 映射；由路由器端口转发直接指向目标设备，可保留真实访问者 IP。
- 默认使用 UPnP IGD 自动上级路由映射，可手动选择 NAT-PMP 或不使用；已有规则的显式选择保持不变。
- Linux `iptables` 自动放行通道端口（每条规则可选）。
- 每条规则保存动态公网地址、端口、IP4P 地址、本地端口、运行状态和日志。
- 日志统一使用东八区时间，刷新时保留阅读位置；所有规则的磁盘日志合计最多 1 GiB，自动轮转。
- 支持将状态文件用于 DDNS：`data/state/<规则 ID>.json`。
- 默认每 10 秒进行一次 STUN/保活心跳；连续缺失心跳会自动重建映射。
- 可选独立公网探针：TCP 验证通道握手，UDP 验证映射引擎健康回显；两者均不依赖目标服务是否启动。
- 映射成功或公网端点变化后，可调用指定 GET 或 POST Webhook；保活心跳不会重复触发。
- 登录页与控制台顶栏显示当前版本号（`v1.00`）。

映射核心使用 [NATMap](https://github.com/heiher/natmap) 的 MIT 许可实现，管理服务、规则存储、路由映射适配和界面为本项目独立编写。UPnP 是本项目的上级路由映射方式，不是 STUN/流量转发引擎；默认选择 UPnP 不等于停用底层 NATMap 引擎。

## 部署

此类程序必须运行在需要暴露服务的主路由或内网设备上，Docker 必须使用宿主机网络；容器 NAT 网络会破坏端口映射。

`network_mode: host` 面向 Linux 主机/路由器。Docker Desktop（macOS/Windows）会将 host 网络指向其 Linux VM，管理端口和 NAT 映射均不等同于桌面宿主机；可用于构建验证，但不能替代在目标 Linux 路由设备上的部署。

```sh
export STUNMAP_ADMIN_USER=admin
export STUNMAP_ADMIN_PASSWORD='use-a-long-random-password'
docker compose up -d --build
```

访问 `http://设备地址:16888`，在登录页使用上面的账号密码登录。

## 认证与会话

- 未登录访问管理页面会跳转到内置登录页；登录成功后签发 `HttpOnly`、`SameSite=Strict` 的会话 Cookie，有效期 12 小时。会话保存在内存中，服务重启后需重新登录。
- 同一来源连续输错 5 次密码会暂时锁定 5 分钟，成功登录后计数清零。
- 脚本或 API 客户端仍可使用 HTTP Basic Auth，凭据与登录页一致。
- 管理页面带 CSP，页面与 API 均返回 `X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff` 等安全响应头；通过反向代理启用 HTTPS 且传递 `X-Forwarded-Proto: https` 时，会话 Cookie 自动附带 `Secure`。

首次建议创建一条 TCP 本机代理转发规则：

| 字段 | 示例 |
| --- | --- |
| 穿透类型 | `IPv4 TCP` |
| 通道监听端口 | `0`（随机）或未被占用的高端口 |
| STUN 服务器 | `turn.cloudflare.com:3478` |
| TCP 保活服务器 | `www.cloudflare.com:80` |
| 转发模式 | `本机代理转发` |
| 上级路由映射 | `UPnP IGD`（默认，路由器需启用 UPnP） |
| 目标地址 / 端口 | `192.168.1.20` / `443` |

运行后页面会显示 `公网映射 IP:端口`。这是 STUN 观测到的地址，不代表目标服务或外部入站访问已经验证通过。该端口可能变化，应通过状态文件或后续 DDNS 集成同步域名记录。

## 公网可达性探针

STUN 成功证明映射已建立，但不能单独证明外部入站数据包当前仍可到达。需要严格验证时，将探针部署在与家庭网络不同的公网 VPS：

```sh
export STUNMAP_PROBE_TOKEN='use-a-long-random-token'
docker compose -f docker-compose.probe.yml up -d --build
```

在穿透规则的“定制模式”填写：

```text
公网探针地址: http://<VPS IPv4>:16900/probe
公网探针令牌: 与 STUNMAP_PROBE_TOKEN 相同
公网探针间隔: 10
```

探针不会访问目标内网服务。TCP 只验证公网端口的三次握手；UDP 发送 `SMHP:` 健康报文，映射引擎在转发前原样回显。因此即使 `targetHost:targetPort` 尚未启动，健康结果仍可正确反映 NAT 通道状态。探针连续两次失败时，规则会立即重建映射。

## 映射 Webhook

在规则“定制模式”设置 Webhook 地址和方法。首次获取映射、或 STUN 地址/端口变化时会触发一次；每次正常心跳不会重复调用。Webhook 地址和 POST JSON 模板均可使用变量，写法支持 `{{STUN_PUBLIC_IP}}`、`${STUN_PUBLIC_IP}` 或 `{STUN_PUBLIC_IP}`。

- `POST`：可填写 JSON 模板；为空时发送默认 JSON，包含 `event`、规则信息、STUN 映射、本地通道和路由器映射状态。示例：`{"ip":"{{STUN_PUBLIC_IP}}","port":{{STUN_PUBLIC_PORT}},"address":"{{STUN_PUBLIC_ADDR}}"}`。
- `GET`：URL 中可直接使用变量，并自动补充 `event`、`rule_id`、`rule_name`、`protocol`、`public_address`、`public_port`、`private_address`、`private_port`、`ip4p` 查询参数；URL 中已明确提供的同名参数不会被覆盖。

变量列表：`STUN_PUBLIC_IP`、`STUN_PUBLIC_PORT`、`STUN_PUBLIC_ADDR`、`STUN_PRIVATE_IP`、`STUN_PRIVATE_PORT`、`STUN_PRIVATE_ADDR`、`STUN_IP4P`、`STUN_PROTOCOL`、`STUN_RULE_ID`、`STUN_RULE_NAME`、`STUN_ROUTER_IP`、`STUN_ROUTER_PORT`。JSON 模板中字符串变量应放在双引号内；端口变量可直接作为数值填写。

## 环境要求

1. 光猫拨号时，光猫 DMZ 应指向主路由。
2. 优先在主路由运行，此时可将上级路由映射设为“不使用”。若运行在局域网设备，新规则默认使用 UPnP；也可选择 NAT-PMP，或手动将通道监听端口转发到该设备。
3. 放行设备防火墙上的通道监听端口。
4. UDP 规则不支持 bind 直转，必须使用本机代理转发。
5. TCP bind 直转须在路由器上将通道监听端口转发到目标设备/端口。

## 映射后无法访问的排查顺序

1. **先检查目标服务**：从映射程序所在设备访问规则的 `targetHost:targetPort`。连接被拒绝时，先确认服务是否启动、地址/端口是否正确、是否只监听回环地址，以及防火墙是否主动拒绝连接；STUN 或 UPnP 不能修复目标服务不可达。
2. **检查本地通道**：访问状态中的 `privateAddress:privatePort`。目标服务正常、本地通道异常时，再排查 NATMap 转发进程和宿主机防火墙。NoMachine、ADB 等非 HTTP 服务应使用对应客户端测试，不能用网页是否打开作为判断依据。
3. **从真正的外部网络检查**：使用手机移动网络或独立 VPS 测试 STUN 地址。局域网内访问公网地址的结果只代表该访问路径，不能代替异地公网验证；可配置上面的公网探针。HTTP 服务请先使用 HTTP 测试，不要把 HTTPS 握手失败误判为端口不通。
4. **单独检查路由器映射**：查看路由映射错误中的发现、设备描述或 SOAP 操作阶段。发现 IGD 后仍可能无法读取设备描述/控制地址；此时需检查路由器 UPnP 服务、访问控制及网络连通性。日志中的路由 WAN 与 STUN IP 不一致表示还有上游 NAT，但仅此不能判定穿透必然失败。
5. **最后检查域名/Webhook**：IP 与端口可达但域名不可达时，检查 Webhook 是否成功、域名代理的源站地址/端口/协议是否同步。Webhook 的 HTTP 502 不等同于 STUN 映射失败。

UPnP/NAT-PMP 请求在所有规则间串行执行，不阻塞每秒的本地心跳检查。同一通道不会并发映射；失败后按 10、20、40 秒递增退避，最长 5 分钟。UPnP 发现/传输故障另有共享冷却，避免多条规则同时冲击路由器。设备描述及控制请求具有完整响应超时，错误会标明失败阶段。

UPnP 使用 STUN 实际报告的本地 IPv4 作为发现源地址及映射目标，而不是任取第一张网卡。有效租约在半个租期时续约；只接受永久租约的路由器在返回 725 时重试永久映射，并每 30 分钟重申一次。停止或重建通道会取消待执行/进行中的管理请求，忽略旧请求的迟到结果。取消请求不会删除已经在路由器上创建的条目，尤其是永久租约；不再需要的旧条目可在路由器中手动清理。

## 日志时间、查看与轮转

- 页面及新写入的规则日志统一显示东八区（UTC+8），例如 `2026-11-06T10:34:01.391+08:00`。不依赖服务器或浏览器所在时区；页面也会把旧的 UTC 日志转换显示，历史磁盘内容不做批量改写。
- 页面每 5 秒更新状态，但不再重建规则卡片。展开日志后，停在底部会跟随最新日志；向上翻看或选中文字时暂停更新正文，保留滚动位置、选区和焦点。出现新日志时点击“有新日志 · 查看最新”恢复跟随。API 仍只返回最近 80 条；暂停期间只缓存最新快照，不无限积累内存。
- 默认每个新日志文件最多 **16 MiB**，达到阈值前轮转为 `<规则 ID>.log.<时间戳>-<唯一编号>`，当前日志仍为 `<规则 ID>.log`。
- **所有规则的当前日志和归档文件合计最多 1 GiB（1,073,741,824 字节），不是每条规则 1 GiB。** 超额前优先清理最旧的归档；如仍不足，再清理最旧的其他规则日志。删除规则后留下的历史日志也计入预算。
- 启动时检查已有日志。总预算内的旧大文件不会被截断，在下次写入时轮转；单个旧文件已超过总预算时，以小块读写保留最新尾部，再执行总量清理，避免一次把整个文件读进内存。旧归档可能大于新文件的 16 MiB 阈值，但同样受总预算约束。
- 单条超长日志会按字节数截断并标记，避免绕过上限；写盘失败不会中断规则运行，最近的内存日志仍可查看。

可通过环境变量调整后重建/重启应用（总预算不能超过 1 GiB）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `STUNMAP_LOG_MAX_BYTES` | `1073741824` | 所有规则日志合计字节上限，可调小 |
| `STUNMAP_LOG_FILE_BYTES` | `16777216` | 新文件轮转字节阈值；未设置时自动取 16 MiB 与总预算的较小值 |

两个值均须为至少 64 的整数，单文件阈值不得超过总预算。日志位于 `STUNMAP_DATA_DIR/logs`（容器中为 `/data/logs`）；请勿让多个服务进程同时写入同一目录。

Compose 另为主服务和可选探针的 Docker 标准输出日志配置 `10m × 3` 轮转，独立于上述规则日志预算。已有容器需重新创建才能应用 Docker 日志配置；仅重启旧容器不会更新该配置。

## 本地开发与验证

无需安装 npm 依赖：

```sh
STUNMAP_ADMIN_PASSWORD=dev-password npm test
STUNMAP_ADMIN_PASSWORD=dev-password NATMAP_BIN=/path/to/natmap npm start
```

测试覆盖认证、规则校验、UPnP 默认值及显式配置保留、创建/停止/删除、东八区日志时间、跨规则日志轮转与总上限、UPnP 发现与响应兼容、源地址选择、超时、请求串行化、退避、续约及取消。未设置 `NATMAP_BIN` 时会跳过两项真实引擎转发测试。浏览器回归会自动寻找常见位置的 Chrome/Chromium，也可设置 `CHROME_BIN=/path/to/chrome`，检查展开日志、滚动、选区、焦点、暂停/恢复跟随及编辑默认值；没有浏览器时仅跳过该项。真实公网 NAT 映射还必须在目标网络中验证，不能以本机回环结果代替。
